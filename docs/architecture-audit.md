# Architecture audit — registry composition, core, contracts, cli

Audit run with 5 independent auditors (registry composition, vendored-code lifecycle, scalability scenarios, core+contracts, cli), each followed by an adversarial verifier that re-checked every finding against the code and SPEC.md. Scope: `registry/`, `packages/core`, `packages/contracts`, `packages/cli`; component internals out of scope. Findings are judged against SPEC intent; "not yet built but additive" is not a finding.

Result: 27 findings raised, 0 refuted outright, 19 downgraded by verification. **0 critical, 0 high.** Severities below are the verifier's.

## Verdict

The per-component composition model is sound and scales without per-component CLI code: manifests are generated from `setup` via the kernel's own `describe()` and drift-checked; `registry.json` and schemas are derived and compared byte for byte; components couple only through capabilities; `doctor`/`remove` judge the real composed app. The weak layer is **above** components (presets relying on unique providers, contracts compatibility not expressible) plus one concrete SPEC violation (K2 in deployment-docker).

### registry-lifecycle-kit-refresh-unchecked [high->medium, partially-confirmed, does-not-scale, cost M, breaking false]
Every `pikit add` replaces the project-wide kit under all installed components, and never checks those components against it
EVIDENCE:
- packages/cli/src/commands/add.ts:92: `refreshKit(projectDir)` runs on every add, whatever the component, and rewrites all four kit packages (vendor.ts:123-129, pointAtKit 138-166).
- packages/cli/src/commands/add.ts:211 and 440-449: `checkCompatible` checks only the manifest being added, and only against @pikit/core (`requires.pikit`). The components already installed are never checked.
- packages/cli/src/project/package-json.ts:46: for a kit package the component's declared version is thrown away (`isKitPackage(name) ? vendorKitPackage(...) : version`). The `@pikit/contracts` version each component declares (CHANGELOG.md:326-327 says components list it 'with its own version') is never compared to anything. checks.ts:42-43 limits `requires.pikit` to @pikit/core.
- packages/cli/src/project/vendor.ts:16-17 justifies this with 'The core only grows within a major (SPEC P7)'. But SPEC K8 says the contracts 'stay 0.x and experimental on their own schedule', and CHANGELOG.md:311-323 records a breaking move of names from core to contracts that required hand edits to projects.
- packages/cli/src/commands/add.ts:106-110: old tarballs are pruned before `doctor` runs. If doctor then finds problems, it throws with the new kit already in place and nothing rolled back. Doctor only composes the app (`setup`, doctor.ts:1-3), so a contract change that breaks `start()` or types still passes.
IMPACT: When contracts change, `pikit add <unrelated>` silently moves every older vendored component (which the user cannot upgrade: `pikit upgrade` does not exist) onto contracts it was not written for. The damage shows at runtime or in `tsc`, not at add time, and the old tarballs are already deleted. The number of components exposed grows with every install.
FIX: In `checkKit`, before any write: for each installed component, compare its recorded kit ranges (pikit.json already stores `dependencies['@pikit/contracts']`, plus `requires.pikit`) with this CLI's kit package versions, and refuse or list the incompatible ones. Bump the contracts version on breaking changes so the check means something.
VERIFIER: The mechanics are as described. add.ts:92 calls refreshKit on every add. vendor.ts:123-166 rewrites the kit dependencies and overrides. checkCompatible (add.ts:440-449) checks only the manifest being added against coreVersion(). package-json.ts:46 replaces a kit package's declared version with the vendored specifier. checks.ts:42 treats only @pikit/core as covered by requires.pikit. pruneVendor runs before doctor (add.ts:106-107), and doctor only composes the app ('never a start', doctor.ts:1-3; no tsc). What the report leaves out: every kit package is version 0.0.0 (packages/*/package.json:3), and every component declares @pikit/contracts 0.0.0 and pikit 0.0.0. The proposed range comparison therefore has nothing to compare today; the auditor half-admits this with 'bump the contracts version'. vendor.ts:1-21 describes the mechanism as interim ('until they are published'). A second copy of core is ruled out (vendor.ts:9-10), so leaving the old kit in place is not possible either: the added component needs this CLI's kit. The only real alternative is refusing. The pruned tarballs are the project's committed vendor/ files, so git restores them. 'Does-not-scale' overstates it: this is a missing guard (correctness risk) for pre-1.0 breaking contract changes, which the maintainers currently handle with CHANGELOG migration notes (CHANGELOG.md:311-323). features/kit-follow-ups.md:24 expects copied components to take contract breaks through `pikit upgrade`. The core point holds: already-installed components are never checked against the new kit, and vendor.ts:16-17 cites P7 (core) while ignoring K8's separately versioned 0.x contracts.
CORRECTED: `pikit add` replaces the project-wide kit (including the 0.x @pikit/contracts) under every installed component. The only guard is commit-ancestry downgrade refusal, and installed components are not checked against the new contracts, so a breaking contract change surfaces at start or in tsc rather than at add time. Today this is a pre-publication correctness gap, not a structural flaw: all kit versions are 0.0.0, so a version check has no signal until contracts versions are actually bumped on breaking changes. vendor/ is committed, so git can recover the old tarballs.

### registry-lifecycle-force-reinstall-orphans [medium->medium, confirmed, correctness-risk, cost S, breaking false]
`add --force` (what the CLI tells users to run instead of `upgrade`) leaves dropped files untracked and keeps env and dependency records stale, so a later `remove` is not clean
EVIDENCE:
- packages/cli/src/commands/add.ts:209: 'pikit upgrade is not built yet (pass --force to reinstall it)'.
- add.ts:235-241 replaces `project.components[name].files` with only the new version's files. applyPlans (add.ts:328-340) copies only those, and add.ts:365-368 deletes the bases of the old hashes. Nothing deletes files the new version no longer ships.
- add.ts:227: the `.env.example` block is only appended when `# <name>` is absent, so variables added by the new version never appear, while pikit.json records them (add.ts:243).
- add.ts:241 records the new `manifest.dependencies`, but package-json.ts:48-53 keeps any existing version (only a warning). A dependency the new version dropped stays in package.json and is no longer recorded, so `remove` (remove.ts:84-87) can never clean it up.
- Reproduced in a temp project with a copy of log-events in a local registry: v1 ships extra.ts plus env FOO; v2 drops extra.ts and adds env BAR; `add --force --yes`. Result: `src/pikit/log-events/extra.ts` stays on disk but is missing from pikit.json; pikit.json environment is [BAR, FOO] but `.env.example` has only FOO; after `pikit remove log-events`, `src/pikit/log-events/extra.ts` is still there.
IMPACT: Until `upgrade` exists, taking an upstream fix leaves untracked stale files (which can still be imported or type-checked), a `.env.example` that does not list required variables, and npm packages that no command will ever remove. That breaks P3's clean removal after one reinstall.
FIX: In planInstall/applyPlans on a reinstall: delete the previously recorded files that the new plan does not ship and whose hash is unchanged (list modified ones and refuse without --force), and replace the component's `.env.example` block instead of skipping it. Ideally, route these through the future `upgrade` so the same diff logic serves both.
VERIFIER: planInstall (add.ts:235-247) replaces the component's recorded files with the new version's only. applyPlans (add.ts:328-340) copies only plan.files, and unreferencedBases (add.ts:365-368) drops the old bases. Nothing deletes files the new version no longer ships, and remove deletes only the recorded files (remove.ts:66-69), so the orphan survives removal. The .env.example block is skipped when '# <name>' already exists (add.ts:227), while pikit.json records the new environment (add.ts:243). The new manifest.dependencies are recorded (add.ts:241), and addDependencies keeps existing versions and only warns (package-json.ts:48-53). A dropped dependency is no longer in installed.dependencies, so unneededDependencies (remove.ts:184-189) never considers it. The CLI itself points users to --force (add.ts:209). The code paths match the auditor's reproduction; I did not re-run it. Medium is proportionate: this is the de facto upgrade path, and one reinstall is enough to break P3.
CORRECTED: 

### registry-lifecycle-remove-not-transactional [medium->low, partially-confirmed, correctness-risk, cost S, breaking false]
`remove` writes step by step with no rollback; a failure after the first write leaves a half-removed project and permanently skips cleanup of providers installed for the component
EVIDENCE:
- packages/cli/src/commands/remove.ts:64 (writes pikit.config.ts), 66-69 (deletes files), 80 (writes pikit.json), 90-91 (writes package.json, then `bunInstall`). None of it is protected by an Undo, unlike add.ts:85-103 and its Undo class (add.ts:377-422).
- remove.ts:95-97: if `doctor` reports problems it throws before remove.ts:99 `installedOnlyFor(...)`. Providers installed for the component keep `installedFor: [<removed name>]`, and only remove.ts:111 ever reads that field. Re-running `pikit remove <name>` fails with 'is not installed' (remove.ts:47), so they are never cleaned up automatically.
- This is the expected path with `remove --force` when the app does not compose (remove.ts:147-150 skips the checks), because the doctor that follows fails too.
- install.ts:15-17: a failed `bun install` throws after package.json was rewritten, leaving bun.lock out of step with it (add.ts's own comment at 82-83: 'a package.json that bun.lock does not match fails the next frozen install').
IMPACT: A remove that fails partway exits non-zero after deleting files and rewriting records. The project's frozen install (Docker build) can break, and providers brought in by `add` stay installed with no command that knows to remove them. That is the opposite of 'add then remove leaves no trace'.
FIX: Reuse add's Undo in remove for the files, pikit.config.ts, .env.example, pikit.json, bases, package.json and bun.lock, restoring on a failed `bun install`. Run the `installedOnlyFor` cleanup (or at least record the leftovers) before the final doctor check, and treat doctor as a report, not a reason to skip cleanup.
VERIFIER: True: remove.ts writes step by step with no Undo (remove.ts:64, 66-69, 80-82, 90-91), and a failed bun install (install.ts:15-17) leaves package.json rewritten against a stale bun.lock, unlike add.ts:85-103. Also true: if the final doctor fails (remove.ts:95-97), installedOnlyFor (remove.ts:99) never runs. installedFor is read only at remove.ts:111, so the offered provider keeps a stale installedFor, and running `pikit remove <name>` again fails at remove.ts:47. Overstated: the doctor-failure path does not leave a 'half-removed project'. By then the component is fully removed (config, files, env block, pikit.json, bases and deps). Only the automatic cleanup of the offered provider is skipped, and that provider stays a normal installed component the user can `pikit remove` directly, so it is not left 'permanently'. The ordering is deliberate: pikit.config.ts is edited first so a shape error aborts before any deletion (remove.ts:56), and modified files are refused before any write (remove.ts:51-54). The only realistic mid-flight failure is bun install (a network or registry error), which leaves an out-of-sync lockfile that rerunning `bun install` repairs. The consequence is real but modest.
CORRECTED: `remove` has no rollback. A failed `bun install` leaves package.json ahead of bun.lock (a frozen install fails until `bun install` is rerun). When the final doctor reports problems (always the case with `remove --force` on an app that does not compose), cleanup of providers installed for the component is skipped: they stay installed with a stale installedFor and must be removed by hand. The component itself is fully removed in both cases.

### registry-lifecycle-dependency-ownership [low->low, confirmed, correctness-risk, cost S, breaking false]
pikit.json records the dependencies a component declared, not the ones `add` actually added, so `remove` deletes dependencies the project had before
EVIDENCE:
- packages/cli/src/commands/add.ts:241-242 records `manifest.dependencies` / `devDependencies` whole. package-json.ts:47-53 adds only the missing ones, and applyPlans (add.ts:343-351) knows which were `added` but does not record it.
- remove.ts:184-189 `unneededDependencies` removes any declared package that no other component declares and no scanned source file imports. A devDependency used through a binary (`bunx wrangler`, scripts) or from a non-JS file is never imported.
- Reproduced: a temp project whose package.json already had `@pikit/contracts` before `add log-events`. `pikit remove log-events` printed 'removed (and the npm packages only it used: @pikit/contracts)' and deleted that pre-existing dependency.
IMPACT: Removing a component can delete a dependency the user added themselves (e.g. an existing `wrangler` devDependency when `deployment-cloudflare` is removed), leaving the project different from before `add`, which P3 forbids.
FIX: Record in pikit.json only the dependencies `addDependencies` returned as `added` (for example an `addedDependencies` list), and have `remove` consider only those.
VERIFIER: add.ts:241-242 records manifest.dependencies and devDependencies whole. addDependencies returns 'added' (package-json.ts:57), but applyPlans uses it only for dependenciesChanged (add.ts:343-351) and never records it. remove.ts:184-189 removes any declared package that no remaining component declares and no project source imports; it excludes only @pikit/core and the extension alias. A pre-existing package the user added and never imports, such as a binary-only devDependency like wrangler, is therefore removed. The auditor's @pikit/contracts reproduction is contrived: starter projects declare it (starter.ts:51) and import it from a generated agent file (starter.ts:184), so in practice the import scan keeps it. The design flaw (recording what was declared, not what was added) and the binary-only devDependency case are real. Low severity is right.
CORRECTED: 

### cli-offers-uniqueness [high->medium, partially-confirmed, does-not-scale, cost S, breaking false]
Offered providers depend on there being exactly one provider in the registry; adding a second one silently breaks presets and `pikit add`
EVIDENCE:
- packages/cli/src/project/offers.ts:89 `if (providers.length !== 1) continue;` means that with 2+ providers nothing is offered, and nobody is told.
- registry/presets/telegram.yaml (alias of http) lists no storage.sql provider. It relies on the offer chain channel-telegram -> outbound-durable/submissions-sql/storage-kv-sql -> storage.sql -> storage-sqlite (new.ts:63-65 comment).
- Reproduced with an in-memory registry that adds a server-only `storage-postgres` providing storage.sql: `bun -e` running withOffers(reg, real.preset('telegram'), ['server']). Before: [storage-sqlite, submissions-sql, outbound-durable, storage-kv-sql]. After: [submissions-sql, outbound-durable, storage-kv-sql], so storage.sql has no provider.
- new.ts:117-119: doctor fails, so `pikit new --preset telegram` throws 'the new project has N problem(s)' after writing the whole project. add.ts:98-102: `pikit add channel-telegram` installs, then throws on doctor.
- features/storage-postgres.md plans exactly this component (server, provides storage.sql).
IMPACT: A purely additive registry change (a second provider on the same target, as planned for Postgres) changes other components' install results and breaks the default preset path, with no message pointing to the storage choice. The same happens in any user or third-party registry that adds an alternative provider.
FIX: Make the default explicit instead of relying on uniqueness. Either presets list their storage provider (add storage-sqlite to http.yaml), or the offer picks a provider declared as the default for each target. When there are several providers, report 'X needs storage.sql: choose one of A, B' before writing, instead of skipping silently.
VERIFIER: Reproduced. offers.ts:89 `if (providers.length !== 1) continue;`. I ran a copy of the real registry with an extra `storage-postgres` manifest (a clone of storage-sqlite): withOffers(telegram, ['server']) lost storage-sqlite, going from [storage-sqlite, submissions-sql, outbound-durable, storage-kv-sql] to [submissions-sql, outbound-durable, storage-kv-sql]. The default `http` preset also relies on this offer: without any extra provider, withOffers(http) gives [storage-sqlite, submissions-sql]. So both server presets are exposed. telegram-cloudflare and cloudflare-minimal list storage-do explicitly and are not. The rule is a deliberate choice, not an oversight. The offers.ts header (lines 11-13) says 'Only when the registry has exactly one provider ... with several, choosing is the user's, and `pikit doctor` says what is missing'. 'Silently' is also wrong: planInstall runs warnUnprovided (add.ts:212, 455-479) for every planned component, offered ones included, so the user gets 'outbound-durable requires "storage.sql", which no installed component provides yet'. doctor names the missing capability too. For the first-party registry, e2e-telegram.test.ts:50-53 runs `pikit new --preset telegram` and would fail the moment storage-postgres is added, so the regression cannot ship unnoticed. The cost the SPEC and the code comment did not account for is still real: the presets depend on registry-wide uniqueness without saying so, and a third-party registry that adds a second provider breaks `new` only after the project is written. The fix is as cheap as claimed.
CORRECTED: By design (offers.ts:11-13), offers need exactly one provider per target. Both server presets (http and telegram) rely on the storage.sql offer instead of listing storage-sqlite. A second server provider of storage.sql, such as the planned storage-postgres, makes `pikit new --preset http|telegram` fail at doctor after the project is written. It is not silent: add/new warn per component and doctor names the missing capability. First-party e2e tests would catch it before release. The real gap is that presets rely on an implicit uniqueness assumption.

`pikit new` is not atomic, and the wizard treats a half-created project as complete
EVIDENCE:
- new.ts:94 writes pikit.json before any component is installed (loop at new.ts:96-111), then `bun install` (new.ts:114, needs the network) and doctor (new.ts:117-119). Nothing is cleaned up if a step fails.

IMPACT: If `bun install` fails (network) or doctor fails, the installer's guided path loops. Configure's scripts fail without node_modules, `up` fails on doctor or finds no deployment-*, and the wizard keeps saying 'run pikit new again'. The only way out is deleting the directory, which nothing tells the user.
FIX: Create the project in a temporary sibling directory and rename it on success, or delete projectDir when newProject throws before it completes. Alternatively write a marker (such as pikit.json `creating: {preset, with}`) and let the wizard resume or refuse based on it.
VERIFIER: Confirmed parts: new.ts:94 writes pikit.json before the install loop (96-111), then bunInstall (114) and doctor (117-119), with no cleanup on failure. new.ts:53 refuses a non-empty directory. wizard.ts:129-130 treats any directory with pikit.json as resumable, and wizard.ts:83-85 skips creation. The header (wizard.ts:21-23) and the intro line (wizard.ts:75) promise continuation. CORRECTED: `pikit new` is not atomic. If `bun install` or doctor fails, the directory is left with pikit.json, and a later wizard run treats it as a finished project to configure. Components are normally all installed by then, since refusals are checked up front, so the practical gap is that nobody tells the user to run `bun install` (or delete the folder). Missing components are not a realistic outcome.

The starter hardcodes specific registry components and model providers, and `new` fails for presets that differ from them
EVIDENCE:

VERIFIER: Checked starter.ts:28-36 (STARTER_WIRING for runtime-pi, STARTER_CONFIG for router-basic) and 173-179 (STARTER_MODEL by target), and new.ts:88, 97 and 107-110. references.ts:32-34 derives the model.provider key from the agent's model, and doctor.ts:83 counts brokenReferences as problems. The 'renaming createRuntimePi' risk is limited because `new` uses the CLI's builtin registry by default. The model/provider mismatch is a real latent trap for third-party or future presets. Severity is overstated.
CORRECTED: The starter deliberately hardcodes two component-specific lines, applied only when those components are installed, and a starter model per target. The model is the real coupling: a preset that installs a different model provider on a target produces an agent whose provider is missing, and `new` fails at doctor after writing. No current preset triggers this.

### cli-deployment-protocol-implicit [medium->low, partially-confirmed, does-not-scale, cost S, breaking false]
The CLI-to-deployment protocol (commands, arguments, result shapes) is undeclared, unvalidated, and hardcoded to the two existing components
EVIDENCE:
- deployment.ts:90-115 printStatus switches on `deployments` (deployment-cloudflare) versus `containers` + `ready` (deployment-docker). Any other shape prints 'no containers' and 'GET /ready: undefined'.
- deployment.ts:83-87 deployedAt reads `{version,url}` by convention. deployment-module.ts:36 AppExec and deployment.ts:128-131 `main.ts` fallback for dev are also conventions only.
- registry/commands.ts:86-104 validates `hooks` exports (SPEC §3.2), but nothing validates that a deployment-* exports up/down/restart/logs/status (`rg deployment packages/cli/src/registry/commands.ts` has no match). A missing export is found only at run time (deployment.ts:69).
- Discovery goes by name prefix: deployment-module.ts:15,43, doctor.ts:79, checks.ts:40. packages/contracts has no deployment type.
- features/deployment-systemd.md plans a third deployment-* that 'exports up, down, restart, logs, status (and exec)'.
IMPACT: Every new deployment component either copies Docker's or Cloudflare's result shape or needs a CLI change to print status. - Components depend on capabilities, never on components: the schema rejects requires.components with an explicit message (checks.ts checkManifest), and checkImports rejects relative imports into a sibling component's files.
- The kernel resolves composition: missing or ambiguous providers and cycles fail with actionable messages ('select one with config.capabilities[...]', packages/core/src/capabilities.ts:134). `pikit doctor` composes the real app, and `pikit remove` decides dependents from the live describe(), not from manifests, so project components count too.
- The Cloudflare two-App model is declarative and checked: `apps.worker` plus generated `halves`, the `<name>-worker` export name enforced at generate/validate time (commands.ts generatedFor), and offers and unprovided-capability warnings computed per App (apps.ts declaredByApp).
- Offers are decided by capabilities and the catalogue's `offer` flag, never by component names, and they back off honestly when there is a choice (more than one provider) instead of guessing.
- The capability catalogue is type-mapped over the declaration-merged AppCapabilities/AppKeyedCapabilities, so a missing, stale or wrong-mode entry fails tsc. Stability requires two providers (checkStability).
- Variant duplication is small, deliberate (C6) and documented. channel-telegram vs channel-telegram-webhook: format.ts differs by 6 of 74 lines (comments), transport.ts by 9 of 70 (error prefix), and api.ts adds the webhook methods. conversations-file vs conversations-kv and sessions-jsonl vs sessions-sql are genuinely different implementations, not copies. No missing abstraction in contracts is evident.
- Presets are declarative (a list of add calls plus kind-based questions and one-level aliases), schema-validated, and never read by name after install ('Nothing reads which preset a project came from').
- Manifests are derived, not hand-kept: provides/requires/optional/halves/replay are generated by running setup through the real app.describe(), and validate reports drift (packages/cli/src/registry/describe.ts, commands.ts checkDrift). This scales to 150 components with no per-component CLI code.
- Components are found by listing `components/`; registry.json is generated sorted and checked byte for byte, so the index never goes stale (commands.ts generate/validate).
- admitInbound in @pikit/contracts is the protocol in code, shared and not vendored: an inbound anchor (tenant, conversation.resolve, dedup) reaches every channel with no edits to copied sources.
- The capability catalogue is typed over AppCapabilities/AppKeyedCapabilities, so a catalogue entry cannot drift from its contract (capabilities.ts), and `stable` requires two providers (checkStability).
- Presets choose by kind (`choose: kind: channel`): a new channel-* component becomes an answer to `pikit new` without editing any preset (registry-source.ts slots).
- Pipelines are open and augmentable per component (channel-http's own http.authenticate) with no anchors, so hooks can be added without a kernel change (packages/core/src/pipeline.ts).
- The C2 mailbox/inbox handler registration avoids the dependency cycle, and gives replicas and Cloudflare the same seam (a mailbox provider swap).
- Content-addressed bases (pikit-bases/) are already written at install, so the P6 three-way merge is purely additive (bases.ts, add.ts applyPlans).
- Kit downgrades are refused by git ancestry (vendor.ts compareKits, add.ts checkKit) rather than by guessing from hashes.
- Import boundaries (no sibling-component imports, Pi only through the adapter, node:/bun:/cloudflare: tied to targets) are enforced per file by registry validate (checks.ts checkImports).
